## 0. What "default behaviour" means here

All three new mode switches are `calloc`-zero after `c5x_new()` and are NOT cleared by `c5x_reset()` (new core :76–85 touches neither `legacy`, `xint_mode` nor `cyc_model`):

- `legacy` (new :36, setter :613 `c5x_set_legacy`) — default 0.
- `xint_mode` / `xint_first` (new :36, setter :611 `c5x_set_xint_mode`) — default 0 / 0.
- `cyc_model` (new :36, setter :612 `c5x_set_cycle_model`) — default 0.

Verdicts below are for that default unless a row says otherwise. Opt-in effects are documented separately in §3. A harness that calls a setter once keeps that mode across every later `c5x_reset()`, because reset never clears these fields.

## 3. Default behaviour vs the opt-in modes

Judged on default (all switches 0), as tasked. The opt-in modes in my areas:

- **`legacy & 8` (TIM reset 0).** Manual-wrong, not accidentally right. With the bit set, `c5x_reset()` :84 restores TIM=0 — the old 05f P-05 / 05g M32 violation (spurious TINT ~1 prescaler period after reset). There is no manual basis for a TIM=0 reset option: 09a §9.1.3 item 6 and Table 4–16 both say FFFFh. The default (bit clear) is the manual-correct value; the legacy bit preserves the bug, it does not preserve a hardware mode. Note `legacy` is never cleared by reset, so one `c5x_set_legacy(…, 8)` call poisons every subsequent reset.
- **`xint_mode = 1` (XINT only after a DXR write, plus one initial kick).** Directionally towards the manual but not manual-correct: (i) the first tick after `c5x_set_xint_mode()` raises XINT with no DXR write ever having happened (`xint_first=1`, :609) — the manual allows XINT only after a DXR write since the last transmit (09b Table 9–13); (ii) RINT is still raised on every tick regardless of mode; (iii) SPC reset state is still ignored (N-5) in both modes; (iv) there is still no XSR/RSR copy model, so the "0→1 transition" is approximated by `dxr_pending = !xrdy` — which is itself corrupted by N-17 (a DXR write with XRST=0 wrongly clears XRDY, manufacturing a pending transmit for a reset-held transmitter). Verdict for mode 1: PARTIALLY FIXED relative to #4, STILL PRESENT for N-5 and for the first-tick kick. Default mode 0 is exactly the old bug.
- **`cyc_model = 1` (App. B fastest-case table).** Directionally towards the manual for the cycle counts, but (i) the table file is missing so the mode cannot run or be verified at all (§5 R1); (ii) even taken at face value it is the *fastest case* (comment :584) — no wait states, no READY, no MMR-write +1, no interrupt-entry cost, no clock generator — so the timer driven off it (:597) is still not CLKOUT1 time (#3 remains STILL PRESENT in substance, only less wrong in magnitude, by an unverifiable amount); (iii) repeated-iteration cost is hardcoded to 1 (`rep_cont ? 1`, :585), which 05g C33 recorded as [UNVERIFIED] against App. B (App. B gives single-instruction counts only; repeat counts are not in App. B). Default mode 0 is exactly the old instruction-count model.
- **`legacy & 16` / `& 128` / `& 64` / `& 32` / `& 4` / `& 1`.** These gate N-1 (MADD/MADS TRM mirror), #15 (BMAR write-back), #10 (NDX mirror), #9 (INTM/XF shadow), #17 (CRGT/CRLT unsigned), #23 (NORM ACC=0). None changes any verdict in my areas except through the N-8-adjacent MADD/MADS line noted in §2 (no cycle/gate effect) and the #10 NDX mirror, which does not change any 05g pipeline-latency row (P09/P10/P14–P30: MMR writes still apply immediately with no latency, and the mirror changes *which* value is loaded, not *when* it becomes visible).
